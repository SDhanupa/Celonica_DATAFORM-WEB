### Step 6 — Identified Root Cause #2: NOT NULL constraint

The original migration added `nic`, `mobile_number`, `first_name`, `last_name` **without** `nullable()`. On production PostgreSQL, these were NOT NULL columns. `syncUser` calling `User::create()` without these fields caused NOT NULL constraint violations → 500.

Also: `syncUser` catch block was returning `new User(['name' => 'Guest'])` (unsaved model, no `id`) which caused Lighthouse non-null violation on `id: ID!`.

**Fixes Applied:**

1. `schema.graphql`: `syncUser: User!` → `syncUser: User`
2. `UserMutations.php`: Added `'nic' => null, 'mobile_number' => null, 'first_name' => ..., 'last_name' => ...'` to all `User::create()` calls. Catch block now returns `null`.
3. New migration `2026_08_06_072519_alter_users_make_profile_fields_nullable.php` to make columns nullable on production.

**Commit:** `fe0bdce`

### Step 10 — TRUE ROOT CAUSE FOUND

```bash
docker logs celonica-web-backend --since 2m 2>&1 | grep "KeycloakAuthGuard"
```

**Output:**
```
[KeycloakAuthGuard] Looking up sub: b37797d4-f69e-4605-bd06-65a36872b78a
[KeycloakAuthGuard] User not found in DB — needs onboarding
[KeycloakAuthGuard] DB lookup failed: The stream or file 
"/var/www/storage/logs/laravel.log" could not be opened in append mode: 
Failed to open stream: Permission denied
```

## 🎯 TRUE ROOT CAUSE

**`storage/logs/laravel.log` was owned by user `1000` (host user) but PHP-FPM runs as `www-data`.**

When ANY resolver called `Log::info()` or `Log::error()`:
1. Laravel tried to write to `laravel.log`
2. Got **Permission denied** (file owned by user 1000, not www-data)
3. Threw `RuntimeException`
4. Lighthouse caught it and returned **HTTP 500**

**Why local worked:** `php artisan serve` runs as the current user who owns all files.  
**Why production failed:** PHP-FPM runs as `www-data`, which cannot write to files owned by user 1000.  
**Why the volume had wrong permissions:** Docker named volume persisted permissions from the previous deployment where files were owned by host user 1000. The `RUN chown -R www-data` in Dockerfile only runs at BUILD time, but the volume mount overrides those permissions at runtime.

---

### Step 11 — Final Fixes Applied

**Immediate fix (no redeploy needed):**
```bash
docker exec -u root -i celonica-web-backend chown -R www-data:www-data /var/www/storage
docker exec -u root -i celonica-web-backend chmod -R 777 /var/www/storage
```

**Permanent code fix** — `config/logging.php`:
```php
// Before:
'default' => env('LOG_CHANNEL', 'stack'),

// After (production uses stderr — no file permission issues):
'default' => env('LOG_CHANNEL', env('APP_ENV', 'production') === 'local' ? 'stack' : 'stderr'),
```

**Commit:** `fcc7ded`
